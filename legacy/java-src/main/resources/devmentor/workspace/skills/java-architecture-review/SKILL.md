# Java 项目架构评审

## 触发条件

- "帮我看看我这个项目架构有什么问题"
- "这个包结构合理吗"、"该怎么分层"
- "这段代码该放哪一层"、"要不要拆服务"
- 用户提供了项目路径，或默认的代码目录就是他的项目

## 铁律：先取证，再判断

**不要在没有调用 `arch_scan` 的情况下给出任何架构意见。** 凭目录名或文件名猜架构，产出的必然是"建议使用设计模式""注意单一职责"这类空话，对用户零价值。

正确顺序：

1. `arch_scan` —— 拿到包结构、依赖图、体量分布、规则命中清单
2. 对每条要写进结论的问题，用 `arch_file_profile` 或 `arch_read_source` **核实一遍**
3. 只写有证据的结论；没有证据的直觉，明确标成"待确认的猜测"并说明怎么验证

## 评审维度（按此顺序，不要跳步）

| 维度 | 看什么 | 典型缺陷 |
| --- | --- | --- |
| 1. 分层与依赖方向 | 包级依赖图 | 循环依赖、repository 反向依赖 service、controller 直接碰 DAO |
| 2. 职责边界 | 类体量、方法数、最长方法 | 上帝类、一个类同时做 IO 与业务规则 |
| 3. 包结构 | 包内文件数、是否平铺 | 20+ 个类堆在一个包里，没有子域划分 |
| 4. 可测性 | 测试文件数、静态依赖 | 零测试、业务逻辑写死在 controller 里无法单测 |
| 5. 一致性与命名 | 顶层包根、命名约定 | 多个包根、同名概念多种叫法 |
| 6. 可演进性 | 依赖扇出、耦合 | 一个改动要动 5 个包 |

## 输出格式（严格遵守）

**每条缺陷按四段写，缺一段就算没写清楚：**

```text
### 缺陷 N：<一句话，具体到类或包>
- 证据：<文件:行，或具体数字，或依赖路径 a → b → c>
- 影响：<不修会怎样，说具体后果，不要说"不利于维护">
- 改法：<具体到"把 X 从 A 移到 B"，给代码骨架>
- 顺序：<先做哪一步、为什么，以及做完如何验证没坏>
```

**然后给一个优先级表**，按"影响 ÷ 成本"排序，不要按你的发现顺序排。

## 不要做的事

- ❌ 不要列 15 条问题。挑 3~5 条真正影响这个项目的，其余放"次要观察"一句话带过。
- ❌ 不要建议"重写"或"改成微服务"。除非用户明确问，否则默认在现有结构上渐进重构。
- ❌ 不要脱离证据谈原则。每句话都要能指回一个文件或一个数字。
- ❌ 不要假设项目用了某个框架。没看到 Spring 注解就不要说"你的 Spring 配置有问题"。
- ❌ 不要只批评不给路径。每条缺陷必须给出可执行的第一步。

## 重构建议的原则

- **小步可验证**：每一步都要能编译、能跑测试，不要给"先大改再统一修"的方案
- **从边界最清晰的地方开始**：先抽最独立的那块，而不是先动最核心的
- **优先消除循环依赖**：它让所有其它重构都变难
- **承认取舍**：说清这个改动会带来什么代价（多一层间接、多一个类），让用户自己决定
